--------------------------------------------------------------------------
v4 - rule ids, profiles and spatial structure
     (roadmap; Phases 1 and 2 landed 20 Oct 2026)
--------------------------------------------------------------------------
Why this direction
	Up to v3 this tool was a narrator. It found a problem and explained in
	prose why it mattered, which is the part a rule table does badly. What
	it could not do was be cited. "The audit flagged your georeferencing"
	is not something a design team can file, argue with, or close out. A
	finding with an identifier is.

	The second thing it could not do was travel. The tool is run on
	projects in several countries, and every one of them is checked
	against something different - a national e-submission regime, a client
	EIR, a BEP, a joint-venture modelling standard. Each names its own
	schema, its own MVD, its own thresholds, its own list of acceptance
	criteria, and its own words for pass and fail.

	Build any one of those into the tool and it is correct for one project
	and wrong for the rest. So the split is:

	  the rules        what the tool can actually examine. Universal, and
	                   in the source.
	  the profile      what THIS project is being held to. Regional, and
	                   in a JSON file beside the project.

	So the direction is: keep the prose, add the identity, and keep every
	region-specific expectation out of the source.

Phase 1 - rule identity and profiles                     (landed)
	No new parsing, so no cost to a normal run. See "What landed in
	Phase 1" below.

Phase 2 - spatial structure                              (landed)
	IfcBuildingStorey, IfcSpace, IfcRelContainedInSpatialStructure and both
	sides of IfcRelAggregates are now parsed. Five new rules, S01 to S05.
	See "What landed in Phase 2" below.

	This was the single biggest gap in the tool and nothing about it is
	regional - every federated package in every country needs its elements
	on a storey, its storeys agreeing between the disciplines, and its tree
	rooted at the IfcProject.

Phase 3 - BCF export                                     (next)
	Scheduled before the property work because it is small and because it
	changes who can act on the report. A finding in a text file has to be
	found again by hand in the authoring tool; a finding in BCF opens next
	to the element that caused it.

	Every finding already carries element ids and bounding boxes, so the
	viewpoint geometry is in hand, and BCF 2.1 is a zip of markup.bcf and
	viewpoint.bcfv per topic - the same zipfile machinery the .xlsx writer
	already uses, so the no-install promise survives.

Phase 4 - property sets and required-information schedules  (the large one)
	Parse IfcPropertySet, IfcRelDefinesByProperties and
	IfcPropertySingleValue, filtered to the property names the active
	profile actually asks for, so a run without a profile pays nothing.

	Then check each element against a schedule of required properties.
	This is the check every client and every authority wants and no two
	of them define the same way, so the schedule is profile data - a
	versioned file naming entity, property set, property and permitted
	values - and never a table in the source. The same mechanism serves a
	national submission requirement, a client EIR and an in-house BEP
	without the tool knowing the difference between them.

	Whichever schedule is in use, record its edition in the report. A
	requirements list is revised; a tool that checks against last year's
	revision and says nothing about which one it used is worse than one
	that does not check at all.

Phase 5 - the two that need new geometry
	Floor-area coverage by IfcSpace - how much of a storey is actually
	tagged as rooms - is a 2D polygon union against the storey outline,
	not a bounding box question. Doable in the standard library, but it is
	a new geometry capability rather than an extension of the existing
	axis-aligned box code.

	Hard clash detection at a millimetre tolerance is not reachable with
	axis-aligned boxes at all. On MEP it would report thousands of pairs
	that do not touch. Real solid-to-solid intersection needs a geometry
	kernel, and that ends the no-dependency design that is the reason this
	tool can be handed to someone with nothing but Python installed.

	The intent is therefore to tighten the interference pass with a
	structural-element filter and a footprint test, and to keep saying
	plainly in the report that it is a smell test rather than clash
	detection. A profile that lists clash detection as one of its checks
	will show it as "partial" for exactly that reason.

What this tool is not
	It is a pre-check. Where a project is checked by someone else - an
	authority, a client, an independent reviewer - their result is the one
	that counts, and this tool has no access to whatever they run. What it
	is for is the round that happens before that: find the problems while
	they are still cheap to fix, with an explanation of each one attached.

	This is why the profile prints the gaps. A profile lists the checklist
	it is answering, including the items no rule examines yet, so the
	report states which of the asks this run did not look at. A check that
	did not run must not read as a check that passed - the same reason v3
	started counting the elements left out of the duplicate pass.

What landed in Phase 2
	The spatial tree is read: IfcBuildingStorey, IfcSpace,
	IfcRelContainedInSpatialStructure, and the child side of
	IfcRelAggregates, which Phase 1 never kept. Five new rules:

	  S01  Spatial hierarchy rooted
	  S02  Building storeys present
	  S03  Storey agreement across models
	  S04  Elements assigned to a storey
	  S05  Rooms modelled as IfcSpace

	A new SPATIAL STRUCTURE section in the report, a Spatial structure tab
	in the workbook, and an Elements off storey tab when there is anything
	to put on it.

Storeys are compared in the survey datum, not in project coordinates
	This is the part that decides whether the check is worth anything.

	Three numbers are kept per storey and only one of them compares
	between models:

	  the Elevation attribute   relative to whatever datum the authoring
	                            model used. Not comparable.
	  project Z                 the placement chain resolved. Comparable
	                            only while every model shares project
	                            coordinates.
	  the level                 project Z plus the height the model carries
	                            in IfcMapConversion. This is the storey in
	                            the survey datum, and it is what the
	                            package is held against.

	A Revit export made on shared coordinates puts the survey offset in
	the IfcSite placement and leaves IfcMapConversion at zero. One made on
	the survey point puts it in IfcMapConversion and leaves the placement
	at zero. Both are correct and both land on the same real-world level -
	but their raw project Z differs by the whole offset. On the test
	package that is 647 m, so comparing project Z reported every storey of
	a correctly-built package as a disagreement. Reading the level in the
	survey datum reports none, which is the right answer.

How a storey disagreement is graded
	Two different faults, because they have different fixes.

	  [?] one level, several names
	      Nothing geometric is wrong, but anything that groups the package
	      by storey - a federated viewer, a 4D sequence, a BCF issue list -
	      sees two levels where there is one. On the test package the
	      interiors model calls a level "L0 TOC" where the structural model
	      calls it "KD03-L0".

	  [!] one name, several levels
	      The models disagree about where a named level is, so one of them
	      stacks wrong - and nothing in either model looks wrong on its
	      own.

	The second is graded on how far apart they are. A structural model
	carries top of concrete where the architectural model carries finished
	floor level, so a slab-thickness offset under one name is a datum
	difference to confirm rather than a mistake to fix. Within
	--storey-datum it is reported [?] and named as that; past it, [!].
	On the test package every structural level sits exactly 100 mm below
	the architectural one of the same name, which is a datum, not a fault.

	One case is deliberately NOT reported as a storey fault. If taking out
	the difference between each model's own survey height makes the
	disagreement vanish, the storeys agree and the models are hung at
	different heights - which is G05, already reported. Naming it again
	here would send the author to move storeys that are correct, so it is
	graded [?] and pointed back at the anchor finding.

	Storeys within --storey-tol of each other are read as one level of the
	package, which is how a 1 mm rounding difference between two exports
	does not read as two levels.

How containment is judged
	An element is on a storey if it is in an
	IfcRelContainedInSpatialStructure, directly or through its decomposition.

	The inheritance matters. The members of a curtain wall and the flights
	of a stair appear in no containment relation of their own - their
	assembly does, and they belong to whatever contains it. Reading only
	the direct relation would report every one of those parts as loose in
	the file.

	  [!] in no spatial structure at all
	      The element belongs to no storey, so it shows under no level in a
	      receiving system and is skipped by anything that walks the model
	      by storey.
	  [?] held by the site, the building or another container rather than
	      by a storey
	      Correct for external works and for anything spanning the whole
	      building, worth confirming for the rest.

	An element contained in an IfcSpace counts as being on that space's
	storey.

Storeys and spaces that are missing rather than wrong
	S02 and S05 are graded on the package, not on each model, because a
	structural or piping model with no rooms in it is right and eight
	findings saying so would bury the one that matters.

	  S02  a model with no IfcBuildingStorey while the rest of the package
	       has them is [?]: its content cannot be federated by level
	       alongside the others. No storeys anywhere in the package is also
	       [?] - expected of an infrastructure package, where there are no
	       storeys to model, and a gap in a building one.
	  S05  no IfcSpace anywhere in the package is [?]: nothing in it can be
	       checked, scheduled or counted by room. A space that sits on no
	       storey is reported separately, because it is not counted in that
	       storey's area.

What S01 actually walks
	IfcProject at the apex with nothing above it, IfcSite aggregated into
	it, IfcBuilding into a site, IfcBuildingStorey into a building, and
	IfcSpace into a storey, a building or a site - a plant yard has no
	storey to sit on. Anything hanging off nothing is named, with what it
	is called, so it can be found in the authoring model.

What landed in Phase 1
	Every finding now carries a rule id.

	  F01  File readable
	  F02  Schema version
	  F03  Schema addenda consistency
	  F04  Length units consistent
	  F05  View definition / MVD
	  F06  IfcProject present                             new
	  F07  IfcSite present                                new
	  F08  One IfcSite per model                          new
	  G01  Projected CRS declared
	  G02  Level of georeferencing
	  G03  MapConversion agreement
	  G04  MapConversion scale
	  G05  Site anchor agreement
	  D01  GlobalId uniqueness
	  D02  Duplicate elements
	  D03  Probable duplicates
	  C01  Generic proxies
	  C02  Classification completeness
	  C03  Type object PredefinedType rule
	  X01  Geometry coverage
	  X02  Floating elements
	  X03  Interferences

	The ids are printed in the RESULT block, written to the Excel Summary
	sheet and carried in the JSON, so a finding can be referred to by
	name in an email, a BEP, or a comment back from the design team.

	The --json file changed shape to carry them. v3 wrote a bare list of
	models; v4 writes an object - {tool, generated, profile, rules,
	findings, models} - with v3's list under "models". A list had nowhere
	to put the findings, and findings outside the file are what the rule
	ids exist for. Anything reading the old file wants ["models"] now.

	F06 and F07 are presence checks only, and stay that way: proving
	IfcProject is the apex with IfcSite below it needs the relationship
	entities, which Phase 2 added as S01. The two are kept apart because a
	model can hold both entities and still have them hanging off nothing.

	--rules
		Prints the rule table and exits. No model needed. This is the
		list to map a profile against.

	--profile FILE.json
		States what this project is being held to. Everything in it is
		optional.

		  name, version, description
		      printed at the head of the coverage section, so a report
		      says which revision of which requirement it was run
		      against.

		  options
		      the long form of any command-line option, underscored:
		      expect_schema, expect_view, clash, min_classified,
		      geo_tol, dup_tol, float_k and so on. Anything you pass on
		      the command line yourself always wins, so
		      --profile x.json --expect-schema IFC4X3 checks against
		      IFC4x3 whatever the file says.

		      A profile can set what to check for. It cannot set where
		      output goes or which files are read.

		  severity_words
		      what to call the three grades. The grades themselves never
		      change; only the words do, so a report can be read beside
		      a checker that says FAIL / ALERT / PASS instead of
		      FIX / REVIEW / PASS.

		  checks
		      the external checklist the profile answers, each item
		      mapped onto the rule ids that address it:

		        {"id": "A-01", "title": "Models are IFC4 Reference View",
		         "rules": ["F02", "F05"], "cover": "partial",
		         "note": "the MVD is read from the file header"}

		      This drives the PROFILE COVERAGE section, which lists
		      every item with the rules behind it and the grade each one
		      reached - and lists the items with NO rules behind them
		      just the same, marked "not yet". Listing those is the
		      point of the section rather than an omission.

		      A check with no rules is always "not yet", whatever the
		      file claims. A profile may not assert coverage it has no
		      rule for; saying which asks went unexamined stays the
		      tool's statement to make, not the file's.

	profiles/example.json is a worked example of the whole format.

	Keep real profiles with the project rather than in this repository.
	They are project data, they are revised on the project's schedule,
	and the next project will need a different one.

v3 - 19 September 2026
--------------------------------------------------------------------------
What changed
	The report now reads the file header, which nothing else does. The
	ViewDefinition written there is the MVD the export claims to follow, and
	it is checked against the schema the file was actually written as.

	A mismatch means anything reading the header is told the wrong MVD. It
	does NOT mean the wrong export setup was used.

	Revit writes the ViewDefinition by schema, not by the view setup chosen.
	Across a nine-model package from two exporter builds, all eight
	IFC4X3_ADD2 files said "CoordinationView" and the one IFC2X3 file said
	"CoordinationView_V2.0" - and one of those eight came from an IFC4x3
	Reference View [BuildingService] setup. The string records the schema,
	which FILE_SCHEMA already states, and says nothing about the MVD.

	So that combination is reported as [ok] with a note, not as a finding:
	eight identical warnings no author can act on would only bury the real
	ones. It is still not an IFC4 MVD name - buildingSMART replaced the
	Coordination View with the Reference View and the Design Transfer View
	at IFC4 - so the note says to read the export setup and to tell the
	receiving side the intended MVD, because the header will not.

	The check still fires for an exporter with no known artefact, where a
	mismatched header is worth acting on.

	Every geometric element is now checked for whether it says what it is:
	an IfcClass that is not a generic proxy, and a PredefinedType that is
	neither NOTDEFINED nor pushed to USERDEFINED. Elements exported as
	IfcBuildingElementProxy are flagged on their own, because a proxy is an
	element the exporter could not map at all.

	Type objects are now read. v2 skipped them, which left the duplicate
	checker's family-name fallback permanently empty - on the test model, 0
	of 58 type references resolved. They also carry a PredefinedType that
	the occurrence inherits, so an element saying NOTDEFINED whose type says
	BEND is correctly counted as classified rather than flagged.

Geometry the tool could not previously read
	Two gaps made real elements look like they were floating, and both are
	fixed.

	IfcCompositeCurve and its segments were never parsed. Revit writes rolled
	and formed steel sections - channels, angles - as a composite curve of
	line and arc segments, so those profiles had no extent, the solids built
	on them had no extent, and the elements fell back to their ObjectPlacement.
	For Revit structural framing that placement is the storey origin, so every
	affected beam collapsed onto the SAME point and the whole group was
	reported as floating a fixed distance from the model centre. On the test
	model that was 57 beams at an identical 167.5 m.

	Deeply nested booleans hit the recursion guard. A floor slab with 41
	penetrations is 41 nested IfcBooleanResult, and the guard stopped at 32
	before reaching the solid. The first-operand chain is now walked
	iteratively, so nesting depth no longer matters.

	Together these took the structural test model from 79.3% to 100% of
	elements resolved from real geometry, and the floating count from 59 to 2.

	The reason neither was visible: an entity type the parser does not keep is
	not in memory at all, so the reader returned "no extent" before reaching
	the line that records an unreadable type. The model reported "79% resolved"
	with an EMPTY unresolved list, which reads as "nothing to see" rather than
	"a fifth of this model could not be read". Misses are now counted, and the
	DIAGNOSTICS section names them.

How a floating element is graded
	The fence decides what is unusual; a scale-free ratio decides how much it
	matters. "Far" means nothing on its own - it only means something next to
	the size of the model it is far from.

	  [!] detached   displaced by more than --float-detach times the spread
	                 of every element the fence accepted. Something is wrong.
	  [?] outlying   past the fence, but still within reach of the model. An
	                 overhead crane, a rooftop plant item and a lightning
	                 finial all read this way and are all correctly placed.

	The yardstick is measured from the elements the fence did NOT flag, so a
	cluster of strays cannot widen it until it hides inside it - the same
	reason the fence itself uses MAD rather than a percentile envelope.

	On the test package this is what separates two overhead cranes sitting
	5.8 m above the pipework in a 12.6 m building, which are correct, from an
	element 890 m from everything else, which is not.

One schema per package
	A federated set read against two schemas is not one model. Entity
	classes, property sets and georeferencing all differ between IFC2x3 and
	IFC4/IFC4x3, so the schema mix is reported first and everything it
	causes defers to it.

	The hard consequence is georeferencing. IfcMapConversion and
	IfcProjectedCRS were introduced in IFC4. A model still on IFC2x3 has
	nowhere to put either, so it can never reach LoGeoRef 50 no matter how
	the exporter is configured - and the standard "fill in the
	MapConversion" advice is advice its author cannot follow. That model is
	now told to change schema first, and it no longer drags the rest of the
	package down to its own LoGeoRef in the summary.

	By default the majority schema in the package is taken as the target.
	Name one explicitly with --expect-schema IFC4X3 to have every model
	checked against it instead, whichever way the majority falls.

	Three things that follow from a schema mix are deliberately NOT reported
	as separate findings, because they are the same fault counted again:

	  mixed ViewDefinitions   Revit writes the string by schema, so two
	                          schemas always give two strings
	  mixed CRS               the pre-IFC4 model cannot declare one
	  package LoGeoRef 0      driven by the model that cannot be fixed
	                          without changing its schema

How classification is judged
	Per element, worst first:

	  [!]  IfcBuildingElementProxy, or any other generic catch-all class.
	       The exporter could not map the family to an IFC class.
	  [!]  PredefinedType USERDEFINED with no ObjectType and no ElementType.
	       IFC requires one of them; without it nothing states what the
	       element is, and the file breaks a schema rule.
	  [!]  PredefinedType not written at all.
	  [?]  A generic supertype - IfcFlowSegment where IfcPipeSegment was
	       meant. One level short, common in older IFC2x3 exports.
	  [?]  PredefinedType USERDEFINED, described only by the Revit family
	       name. Legal, but "Family450.0001" means nothing to the receiving
	       system.
	  [?]  NOTDEFINED on both the element and its type.
	  [ok] A specific PredefinedType, on the element or inherited from its
	       type. Also classes that have no PredefinedType in IFC2x3 at all,
	       which is the schema's doing, not the modeller's.

	PredefinedType is not always the last attribute. IfcDoor ends with its
	OperationType and IfcStairFlight carries four extra attributes ahead of
	PredefinedType, so the position is read from a per-class table; classes
	not in that table are read by shape and marked "scan" in the Read by
	column of the Classification sheet, so an assumption is never presented
	as a reading.

	Type objects are checked separately for the USERDEFINED / ElementType
	rule and reported under Schema rule. That one is a real schema
	violation: a strict importer may reject the file rather than read it
	loosely.

v2 - 5 September 2026
--------------------------------------------------------------------------
What changed
	Duplicate detection now uses real element geometry instead of the
	ObjectPlacement origin. Revit exports beams and columns with the
	placement sitting at the storey origin and the true position buried in
	the geometry, so v1 reported every beam on a level as a duplicate
	(440 of 637 elements in the structural model - all false).

	Geolocation now reports real-world map coordinates and compares the
	IfcMapConversion of every model in the package. That is what decides
	whether a federated set lines up.

	Length units are read from the IfcProject and applied everywhere.
	Millimetre, metre, foot and inch models all work; nothing assumes mm.

	The floating-element check was rebuilt on a robust statistic and now
	actually fires. v1 could not see a stray element 890 m from the model.

	The report leads with a verdict instead of making you read it all.

How a duplicate is decided
	1. Duplicate GlobalId          -> ERROR, the file is schema-invalid
	2. Same IFC class AND same type/family name AND bounding boxes
	   overlapping by 90% or more  -> DUPLICATE
	3. Same class and type name, roughly coincident but different extent
	                               -> PROBABLE
	4. Overlapping but a DIFFERENT class or type name -> NOT a duplicate.
	   Reported separately as an INTERFERENCE with --clash.

	Overlap on its own is never treated as a duplicate.

	From v3 an element whose body geometry could not be read is left OUT of
	the duplicate check entirely. All it has is a placement origin, which is
	a point rather than an extent, and a pair of points could never be
	graded above PROBABLE however they were compared. The count left out is
	printed per model under DIAGNOSTICS, because a check that did not run
	must not read as a check that passed.

	One consequence is worth knowing: the models with the weakest geometry
	are also the least examined for duplicates. Improving a model's geometry
	resolution restores its duplicate coverage at the same time.

	Pairs that repeat with a constant element-id offset are reported as ONE
	duplicated block rather than N separate findings - that pattern means a
	group was copied in a single action.

How a floating element is decided
	Each element's distance from the model centre is measured, in plan and
	in elevation. Anything past median + 8 x MAD of those distances is
	flagged. MAD (median absolute deviation) tolerates up to half the model
	being stray, so a cluster of strays cannot stretch the limit until it
	hides itself - which is how the v1 percentile envelope failed.

	The limits used are printed above the results every run. If you already
	know the model, give an absolute distance with --float-xy / --float-z.

How georeferencing is judged
	Each model's IfcMapConversion is classed as one of three things:

	  populated    Eastings/Northings/Height are filled in - a real
	               georeference.
	  placeholder  all zeros. The exporter wrote the entity but never
	               filled it in. This is an identity transform, NOT a
	               georeference, and models agreeing on those zeros are
	               not thereby proven aligned. Reported two ways depending
	               on whether the model geometry already carries real-world
	               coordinates, because the fix differs.
	  absent       no IfcMapConversion at all.

	Only populated ones are compared against each other, so a placeholder's
	zeros cannot drag the Eastings spread to a nonsense value.

	Level of georeferencing (LoGeoRef) is reported per model:

	  10  postal address only
	  20  IfcSite latitude / longitude
	  30  IfcSite placement carries the survey offset
	  40  model context WorldCoordinateSystem / TrueNorth
	  50  IfcMapConversion + IfcProjectedCRS   <- the only complete one

	Below level 50 the report prints a HOW TO FIX block aimed at the model
	author, explaining why naming a CRS is not georeferencing and giving the
	Revit steps to correct it. The same text goes on the Georeferencing tab
	of the Excel workbook so it can be issued with the findings.

	The report also compares the REAL anchor - where each model's own origin
	lands in map coordinates - rather than only the IfcMapConversion values.
	When the offset is carried by the IfcSite placement, comparing
	MapConversion alone sees ten identical rows of zeros and reports a false
	pass; comparing anchors catches a model sitting metres from the rest.

	Scale is checked per model, not across models. IfcMapConversion.Scale
	converts project units into CRS map units, so a millimetre model on a
	metre CRS must carry 0.001 and a metre model 1.0. Both are correct, and
	comparing them to each other would report a false mismatch on any
	package that mixes units. Each model is checked against the value its
	own units imply.

Reading the report
	The report answers the question first, then shows the working:

	  RESULT     one line per check, worst first
	               [!]   must fix
	               [?]   review
	               [ok]  passed
	  MODELS     the full file names, each given a short label
	  ...        the detail sections, keyed by those labels

	Models are labelled by the part of the file name that differs - for
	ISO 19650 names that lands on the discipline code (AR, ST, PI...), and
	repeats are numbered (PI1, PI2). Full names appear once, in MODELS, so
	the rest of the report is not 40 characters of shared prefix per line.

	A condition shared by several models is stated once, naming the models,
	instead of repeated per model.

	Interferences are grouped by the pair of classes involved, so a few
	hundred pipe-and-fitting overlaps read as a few lines.

	Output is plain ASCII, so "python ifc_audit.py > report.txt" is safe.

Sharing the results
	  python ifc_audit.py --excel audit.xlsx

	writes a real Excel workbook you can issue to the design team. No add-in
	and no pip install - it is built with Python's own zip library. Every
	sheet has a frozen header row and AutoFilter switched on.

	  Summary                Result block: FIX / REVIEW / PASS per check,
	                         colour coded, with the package name and run date
	  Models                 one row per model - schema, view definition and
	                         MVD check, exporting tool, units, element and
	                         geometry counts, classified share, CRS,
	                         centres, MapConversion
	  Classification         every element flagged on IfcClass or
	                         PredefinedType, with what to do about it, plus
	                         the type objects breaking the USERDEFINED rule
	  Spatial structure      one row per storey per model - the Elevation
	                         attribute, project Z, the level in the survey
	                         datum, the level of the package it fell into,
	                         whether it agrees with the other models and why,
	                         what else the same level is called, and the
	                         elements and spaces on it
	  Elements off storey    every element in no spatial structure, and every
	                         one held by the site or the building rather than
	                         by a storey
	  Georeferencing         LoGeoRef level, anchor coordinates, the offset
	                         of each model from the package median, and the
	                         HOW TO FIX text
	  Duplicates             one row per finding, including reused GlobalIds
	                         and duplicated blocks
	  Interferences by type  overlap counts per pair of IFC classes
	  Interference pairs     every overlapping pair, for filtering
	  Floating               every element flagged as out of place

	Sheets with nothing to report are left out. Add --clash to include the
	two interference sheets.

Options (all optional - "python ifc_audit.py" alone still works)
	--profile FILE.json    apply a submission profile - see v4
	--rules                print the rule table and exit; no model needed
	--excel audit.xlsx     write the shareable Excel workbook
	--json report.json     also write every finding to a JSON file.  From
	                       v4 the file is an object, not the bare list v3
	                       wrote: {tool, generated, profile, rules,
	                       findings, models}, with v3's list under
	                       "models".  A list had nowhere to put the rule
	                       ids, which is the whole point of carrying them.
	--clash                add the interference report (off by default)
	--clash-frac 0.30      overlap share of the smaller element to report
	--dup-iou 0.90         box overlap at or above which a pair is DUPLICATE
	--probable-iou 0.50    box overlap at or above which a pair is PROBABLE
	--dup-tol 10           coincidence tolerance in millimetres
	--geo-tol 1            MapConversion agreement tolerance in millimetres
	--storey-tol 50        storeys within this many mm of each other are read
	                       as one level of the package
	--storey-datum 600     a storey name found at two levels further apart
	                       than --storey-tol but within this is reported as a
	                       datum difference to confirm - finished floor level
	                       against top of concrete - rather than as a fault
	--min-geometry 0.90    flag a model resolving less geometry than this
	--min-classified 0.90  flag a model classifying less than this share
	--expect-schema S      require every model to be on schema S, e.g.
	                       IFC4X3; default is the package majority
	--expect-view NAME     require every model to declare this
	                       ViewDefinition, e.g. ReferenceView_V1.2
	--float-k 8            floating sensitivity; lower is stricter
	--float-detach 4       past the fence, how many times the spread of the
	                       rest counts as detached (FIX) rather than
	                       outlying (REVIEW)
	--float-min 10         floor for the derived float limits, metres
	--float-xy M           override the plan float limit with M metres
	--float-z M            override the vertical float limit with M metres
	--max-rows 20          rows printed per section per model

	Note: in v1, --float-xy was a multiplier and --float-z was a threshold
	that was combined with one. Both are now plain absolute overrides in
	metres, and both are off unless you pass them.

Notes
	Model names print in full; every column widens to the longest name.

	INTERFERENCES is a bounding-box smell test, not clash detection. On MEP
	models it reports pipes overlapping their own fittings at connections.
